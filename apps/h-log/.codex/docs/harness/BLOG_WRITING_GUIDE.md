# H-Log 한국어 기술 글 작성 가이드

기준일: 2026-10-15. `blog-writing-quality / Step 0`에서 준비한 편집 기준이다. Step 1에서 문체·유형별 설명·근거 보존 규칙을 추려 기존 writer prompt에 반영했다. runtime은 이 문서나 설치된 스킬 파일을 읽지 않는다.

## 글의 중심

독자가 문제와 판단을 따라갈 수 있게 쓴다. 기술의 정의만 나열하거나 사용한 도구를 소개하는 데서 끝내지 않는다. 어떤 조건에서 무엇을 선택했고 어디까지 확인했는지 설명한다.

글의 화자는 H-Log 작성자다. 다만 저장소에 코드가 있다는 이유만으로 운영 장애를 겪었다거나 특정 감정·동기를 가졌다고 쓰지 않는다. 구현으로 확인한 동작, 기록으로 확인한 경험, 문서에서 읽은 사실, 이번 글에서의 판단을 구분한다.

## 작성 전에 정할 것

1. **독자의 질문**: 이 글을 읽으면 어떤 판단에 도움이 되는가.
2. **글 유형**: 아래 다섯 article mode 중 근거에 맞는 유형은 무엇인가.
3. **근거와 시점**: 코드·명령·결과·공식 자료가 무엇을 뒷받침하며 언제 확인했는가.
4. **확인 범위**: 로컬 재현인지 운영 관측인지, 실행하지 않은 계획이나 추론은 무엇인가.
5. **공개 범위**: 내부 식별자·원문·경로를 빼도 기술적 설명이 성립하는가.

위 항목은 편집용 질문이다. writer JSON의 새 필드나 공개 화면의 필수 메타정보로 추가하지 않는다. 기존 article mode, sources, claims, evidence와 personal context 계약을 사용한다.

## 제목과 첫 문단

제목은 기술 이름에 다루는 문제나 판단 기준을 붙인다. 측정하지 않은 개선율, 실행하지 않은 전환, 확인되지 않은 장애를 제목에 넣지 않는다.

| 초점이 흐린 제목 | 문제를 드러내는 제목 예시 |
| --- | --- |
| 비동기 렌더링으로 사용자 경험 개선하기 | 최근 글 조회가 늦어져도 홈은 먼저 보여주기 |
| Redis 메시징 완벽 정리 | Redis Pub/Sub을 쓰기 전에 정할 메시지 유실 기준 |

첫 문단은 문제와 글의 범위를 짧게 보여준다. 인사·시대 변화·기술의 중요성 같은 배경을 매번 앞세우지 않는다. 필요한 맥락은 선택을 설명하는 문단에서 보충한다.

글의 요약은 다루는 문제와 읽고 얻을 내용을 1~2문장으로 적는다. 제목을 그대로 반복하거나 확인하지 않은 결과를 예고하지 않는다.

## 유형에 따라 설명 순서를 고르기

| article mode | 사용할 수 있는 근거 | 자연스러운 전개 |
| --- | --- | --- |
| `project_record` | 확인한 구현·변경 기록 | 요구 조건 → 구현 선택 → 실제 동작 → 검증 범위 |
| `ops_incident` | 사건 시점·증상·조치가 남은 운영 기록 | 증상 → 확인한 단서 → 원인과 조치 → 복구 확인·남은 일 |
| `experiment` | 조건·명령·코드·결과가 남은 실행 기록 | 확인할 질문 → 재현 조건 → 결과 → 해석·한계 |
| `document_analysis` | 공식 문서·원출처 | 질문 → 문서에서 확인한 사실 → 판단 기준 → 미확인 조건 |
| `applied_analysis` | 공개 가능한 개인 맥락과 자료 | 적용할 조건 → 선택지 → 예상 영향 → 검증 계획 |

이 순서는 글을 준비하는 기준이며 고정 목차가 아니다. 실패한 시도가 없으면 만들어 넣지 않는다. 직접 실행하지 않았다면 `experiment`나 실험 결과로 표현하지 않는다. 단순 자료 분석을 운영 경험으로 바꾸지 않는다.

## 말투와 문단

- 해요체를 중심으로 설명한다. 짧은 사실 설명에는 합니다체를 섞을 수 있지만 문단마다 말투를 뒤집지 않는다.
- 한 문장에는 중심 주장 하나를 둔다. 조건과 결과가 길어지면 나눈다.
- 명사를 쌓기보다 누가 무엇을 했는지 쓴다. `~에 대한 확인이 이루어졌어요`보다 `~를 확인했어요`가 분명하다.
- `따라서`, `또한`, `결론적으로` 없이도 연결되는 문장은 바로 이어 쓴다.
- 모든 문단에 같은 요약을 붙이지 않는다. 이미 설명한 결론을 맺음말에서 반복하지 않는다.
- `혁신적`, `완벽한`, `압도적인` 같은 평가 대신 동작과 확인 결과를 적는다.
- `저는`, `제가`를 매 문장에 넣지 않는다. 선택이나 해석의 주체를 밝혀야 할 때 사용한다.
- 사실과 판단을 잇는다. 기능을 소개한 뒤 그 기능 때문에 어떤 조건을 확인할지 설명한다.
- 모르는 부분은 해당 주장 옆에 짧게 적는다. 긴 면책 문구를 글 앞뒤에 반복하지 않는다.
- 굵은 글씨·불릿·표는 비교와 절차에만 필요한 만큼 사용한다. 모든 문장을 목록으로 만들지 않는다.

## 사실을 보존하는 교정

작성과 사실 검토를 먼저 마친 뒤 `espada:humanize-korean`으로 한국어 산문을 다듬는다. 실행 환경에서 설치된 SKILL.md와 quick rules를 읽는다. 교정 과정에서는 사실·범위·불확실성·검증 결과를 강화하거나 약화하지 않는다.

다음 항목은 원본과 byte 단위로 보존한다.

- 코드 블록, inline code, 명령, URL, 경로, 식별자, 상태값과 SHA
- 날짜·숫자·단위와 측정 조건
- 제목 구조, 표 구조, 체크박스, 직접 인용

예를 들어 `로컬에서 확인했어요`를 `운영에서도 안정적으로 동작해요`로 고치는 것은 문체 수정이 아니다. `가능성이 있어요`를 `발생해요`로 바꾸는 것도 허용하지 않는다.

근거 부족이나 기술 오류를 발견하면 문체 교정과 분리해 원본의 사실 검토부터 다시 한다. 수정 이유와 근거를 기록한 뒤 새 원본을 교정한다. 자연스럽게 들린다는 이유로 불확실성을 지우지 않는다.

## 같은 뜻을 더 직접적으로 쓰는 예시

다음은 H-Log의 구현 기록에서 일반화한 편집 예문이다. 다른 프로젝트의 성과나 경험을 주장하는 템플릿으로 사용하지 않는다.

| 교정 전 | 교정 후 |
| --- | --- |
| 실패한 경우에 대해서는 최근 글 영역 내에서 안내가 이루어지도록 했어요. | 조회가 실패하면 최근 글 영역에 안내를 보여줘요. |
| 이 제한은 화면에 보여줄 글 수에 대한 것입니다. | 이 값은 화면에 보여줄 글 수를 제한해요. |
| 글 테스트 35개를 다시 실행했고 모두 통과했어요. | 글 테스트 35개를 다시 실행했어요. 모두 통과했습니다. |

자료 분석에서는 적용 의도를 경험으로 바꾸지 않는다.

> 메시지가 빠졌을 때 원본을 다시 조회할 수 있는지부터 확인하려고 해요. 처리 완료를 남겨야 하는 요청이라면 미완료 상태를 어디에 기록할지도 정해야 합니다.

위 문단은 검토 관점을 설명하는 예시다. 실제 Pub/Sub 도입·장애·전환 이력을 뜻하지 않는다.

## 코드·표·그림을 넣는 기준

- 코드는 선택한 동작을 설명하는 데 필요한 부분만 보여준다. 생략한 부분이 있으면 실행 가능한 전체 예제로 오해하지 않게 적는다.
- 비교할 조건이 있으면 표를 사용하고, 흐름이나 책임 구분이 복잡하면 구조도를 검토한다.
- 그림은 관련 설명 옆에 둔다. 다른 사이트의 이미지를 가져오거나 모든 글에 장식용 그림을 채우지 않는다.
- 결과를 제시할 때 재현 조건과 검증 시점을 함께 적는다. 과거 기록 인용과 이번에 다시 실행한 검증을 구분한다.
- 출처는 해당 사실 가까이에 연결한다. 출처의 설명과 작성자의 판단을 같은 주장으로 합치지 않는다.

## 검수 순서

1. 제목·요약·도입부가 같은 질문을 다루는지 읽는다.
2. 직접 경험·자료 사실·판단·검증 계획을 구분한다.
3. 원본과 교정본의 보호 항목을 비교한다.
4. 각 문단에 선택 이유나 구체적인 동작이 있는지 확인한다.
5. 기존 claim/privacy/quality gate를 유지한다. 수동 문체 검토를 gate 통과나 실제 모델 품질 검증으로 대신하지 않는다.
6. 초안, 로컬 미리보기, 공개 발행 상태를 따로 기록한다.

## Step 0에서 준비한 기준 초안

| 제목 | 유형 | 확인한 근거 | 남은 검토 |
| --- | --- | --- | --- |
| 최근 글 조회가 늦어져도 홈은 먼저 보여주기 | `project_record` | H-Log 현재 코드·기존 로컬 검증 기록·공개 글 테스트 35/35 재실행 | 운영 트래픽과 실제 배포 환경은 미측정 |
| Redis Pub/Sub을 쓰기 전에 정할 메시지 유실 기준 | `document_analysis` | Redis Pub/Sub·XREADGROUP·XACK 공식 문서 | 실행·벤치마크 없이 적용 기준만 정리 |

두 글은 아직 비공개 초안이다. 전체 원본·교정본과 claim별 근거는 Git/Docker에서 제외한 로컬 초안 묶음에서 관리한다. 토스 글을 재작성하거나 회사 Wiki 내용을 옮기지 않았다.

Step 1은 `lib/blog-hermes-article-provider.ts`의 기존 단일 호출에 짧은 작성 기준과 자체 점검 지침을 연결했다. provider test double로 지침과 검증 입력의 전달을 확인했으며 실제 모델이 만든 글의 문체를 평가한 것은 아니다. 다음 Step 2에서 초안을 다시 읽고 작성 계약 검증과 수동 문체 평가를 구분해 기록한다.
